# V86のHDD読み取り対応

通常の[HDD単独起動](hdd-boot.md)では、A:が起動元かつ検証済みHDDです。
以下のB:の例は、従来のFD＋APPS HDD構成を対象とします。
従来のKGUI32 PEGC/Cirrus構成では、DOS ShellからA:と検証済みKHD98 HDDを
利用できます。HDDのドライブ文字はDOSの実DPBと常駐ドライバ記録から取得します。
通常はB:です。シェルで `B:`、`CD \APPS`、`DIR` と入力するか、
`TYPE B:\WORK\NOTE.TXT` のように明示します。

各VMが既定ドライブとドライブ別のカレントディレクトリを保持します。
ホストDOSや別のVMの状態は変更しません。ルートアプリはプログラムのディレクトリから
起動し、子EXECは同じVMの状態と読取ハンドルを引き継ぎます。
裸の実行ファイル名はFDルートを優先し、見つからない場合だけ検証済みHDDのAPPSを
探します。破損ファイルやI/OエラーはHDDへのフォールバックを許可しません。

読取・seek・複製・属性取得・ディレクトリ検索・子EXECを扱います。
書込open、作成・書込・削除・rename・属性変更は禁止です。デバイスやUNC、
未検証ドライブも拒否します。PM32 Editorの保存・復旧APIとは別の経路です。
任意のHDD形式と完全なDOS/BIOS互換は対応範囲に含みません。
既存ユーザーディスクの自動更新やフォーマットは行いません。

配布するAPPSの6本は従来どおりです。完全FDによる単独起動も維持します。
`VDOS.EXE` はFD上の診断用DOSアプリです。E2Eは検証用のHDDコピーにだけ
このアプリとデータを追加し、通常配布のHDDには追加しません。

## 検証と互換性

専用のGitHub ActionsはPEGC/Cirrusそれぞれで次の3構成を実行します。

- HDD読取: 70,001バイトの読込と64 KiB超のseek、子EXEC、1501バイトの環境、
  継承ファイル位置、所有DTA、書込可能属性のファイルへの書込拒否、FD優先順位、
  HDD上の元のCOMMAND.COM、PM32時計の同時進行。
- 分離・回収: 二つのV86のドライブ/CWD、開いたHDDハンドルの強制終了・実CPU例外時の
  回収、新しいFDプロセスへの再起動、PM32の継続。
- 非対応媒体: HDDなしと検証不成立のHDDでのFD互換とHDD起動拒否。

実行中のV86 PSPから統計を取得し、実CPUのVMフラグ・例外・資源状態と照合します。
全構成で終了前後のFD/HDD全バイトが不変で、DOS/XMS/ハンドル/ベクタが回収されることを
確認し、JSONとスクリーンショットを成果物に残します。

公開XMS APIの4096バイト、既存ワイヤサイズ、2枠、常駐スタック境界は維持します。
内部の一時領域は1024バイトで、より長い転送や環境を分割して扱います。
ネイティブ側の仕様は [HDD-READONLY.md](https://github.com/kumakumapon/MS-DOS/blob/main/tools/k386/HDD-READONLY.md) を参照してください。

ブラウザE2EはGitHub Actionsで実行します。このチャットでは `npm run preview` や
代替のローカル配信サーバーを起動しません。マージ順はMS-DOS、main CI完了、webnp2、
master CI・Pages公開確認です。
